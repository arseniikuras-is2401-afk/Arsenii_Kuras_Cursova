## 1. Призначення застосунку

Настільний застосунок для майстра-приймальника автосервісу. Він веде облік клієнтів та їхніх автомобілів,
оформлює замовлення-наряди на ремонт (роботи та запчастини), відстежує стан замовлень від приймання авто до
видачі, веде склад запчастин і показує підсумкові показники: виручку, завантаженість механіків, популярні роботи,
запчастини, яких мало на складі.

Користувач один: майстер-приймальник (адміністратор). Методичка авторизації не вимагає, тому її не робимо.

Проблема, яку розв'язує програма: у невеликому сервісі замовлення часто ведуть у зошиті чи Excel. Через це
важко побачити історію ремонтів конкретного авто, порахувати вартість із запчастинами, помітити, що на складі
закінчилася потрібна деталь, і зрозуміти, хто з механіків перевантажений.

## 2. Об'єкти предметної області (таблиці БД)

| Таблиця | Що зберігає | Основні поля та обмеження |
|---|---|---|
| `clients` | Клієнти | прізвище, ім'я (обов'язково), телефон (UNIQUE, формат `0XXXXXXXXX`), email (UNIQUE, може бути порожнім), дата реєстрації |
| `cars` | Автомобілі клієнтів | FK клієнт, марка, модель (обов'язково), рік випуску (1950…поточний рік), держномер (UNIQUE, формат `AA1234BB`), VIN (UNIQUE, 17 символів без I/O/Q, може бути порожнім), пробіг (≥ 0) |
| `employees` | Механіки | прізвище, ім'я, телефон (UNIQUE), спеціалізація (FK категорія), дата прийому, `is_active` |
| `repair_categories` | Категорії ремонту (довідник) | назва (UNIQUE): «Двигун», «Ходова», «Гальма»… Групує і роботи, і запчастини |
| `work_types` | Прайс робіт (довідник) | FK категорія, назва (UNIQUE), ціна за одиницю (≥ 0), нормо-години (> 0), `is_active` |
| `parts` | Склад запчастин | FK категорія, артикул (UNIQUE), назва, ціна продажу (≥ 0), залишок (≥ 0), мінімальний залишок (≥ 0) |
| `orders` | Замовлення-наряди | FK авто, FK відповідальний механік, дата приймання, плановий термін (≥ дати приймання), дати завершення й оплати, скарга клієнта, пробіг при прийманні, ручна знижка % (0–30), знижка постійного клієнта % (0 або 5), статус |
| `order_works` | Роботи в замовленні | FK замовлення, FK робота, кількість (> 0), ціна, зафіксована на момент додавання |
| `order_parts` | Запчастини в замовленні | FK замовлення, FK запчастина, кількість (> 0), ціна, зафіксована на момент додавання; UNIQUE(замовлення, запчастина) |
| `order_status_log` | Історія статусів | FK замовлення, старий і новий статус, дата й час, коментар |

Окремої таблиці оплат немає: оплата фіксується статусом `paid` і датою в `orders`, бо часткових оплат у
задачі немає. Методичка прямо попереджає, що зайві таблиці оцінку не підвищують. Кожна з 10 таблиць
обґрунтована в `docs/02_design.md`.

Зв'язки:
- клієнт 1 — N авто;
- авто 1 — N замовлень, механік 1 — N замовлень;
- категорія 1 — N робіт, 1 — N запчастин, 0..1 — N механіків (спеціалізація);
- замовлення 1 — N робіт, робота (прайс) 1 — N рядків робіт;
- замовлення 1 — N запчастин, запчастина 1 — N рядків запчастин;
- замовлення 1 — N записів історії статусів.

Правила видалення:
- клієнта, в якого є авто, видалити не можна (`ON DELETE RESTRICT`); програма пояснює причину;
- авто, по якому є замовлення, видалити не можна; історія ремонтів має зберігатися;
- роботу з прайсу, запчастину чи механіка, які вже є в замовленнях, видалити не можна; механіка натомість
  деактивують, а роботу або запчастину можна змінювати (ціна в старих замовленнях не зміниться, бо вона
  зафіксована);
- видалити можна лише замовлення в статусі `new` або `cancelled`. Рядки робіт і запчастин видаляються
  каскадно, а запчастини повертаються на склад в одній транзакції.

## 3. Операції предметної області (бізнес-правила)

1. **Оформлення замовлення.** Майстер обирає клієнта, потім його авто, механіка та описує скаргу. Пробіг при
   прийманні не може бути меншим за останній відомий пробіг авто. Одне авто не може мати двох відкритих
   замовлень (`new` або `in_progress`) одночасно. Механіка можна призначити, лише якщо він активний і має
   менше 4 відкритих замовлень.
2. **Додавання запчастини до замовлення** (транзакція). Кількість не може перевищувати залишок на складі.
   Рядок замовлення створюється, а залишок зменшується; якщо будь-який крок не вдався, відбувається відкат.
   Видалення рядка повертає запчастини на склад.
3. **Зміна статусу** з перевіркою допустимих переходів:

   ```
   new ──► in_progress ◄──► completed ──► paid
    │            │
    └────────────┴──► cancelled
   ```

   - `in_progress` можна поставити, лише якщо в замовленні є хоча б одна робота;
   - `completed` фіксує дату завершення й оновлює пробіг авто; неоплачене виконане замовлення можна
     повернути на доопрацювання;
   - кожна зміна статусу записується в історію з датою й коментарем;
   - `cancelled` повертає всі запчастини на склад (транзакція);
   - роботи й запчастини можна змінювати лише в статусах `new` та `in_progress`; для інших статусів кнопки
     неактивні, а підказка пояснює чому.
4. **Розрахунок вартості.** Сума = Σ(ціна роботи × кількість) + Σ(ціна запчастини × кількість) − знижка.
   Постійний клієнт (від 5 оплачених замовлень на момент створення нового) отримує 5 % на роботи
   автоматично. Ручна знижка майстра (до 30 %) діє на роботи й запчастини. На роботи з двох знижок
   застосовується більша, вони не додаються. Гроші рахуються в копійках, без дробових чисел.
5. **Прострочені замовлення.** Відкриті замовлення з минулим плановим терміном підсвічуються в таблиці та
   рахуються на головній сторінці.
6. **Поповнення складу.** Прихід запчастин вручну або імпортом CSV. Запчастини із залишком нижче
   мінімального підсвічуються й показуються на головній сторінці.

## 4. Функціональні вимоги для високого рівня

| Вимога методички (I рівень) | Як реалізуємо |
|---|---|
| CRUD | Для всіх сутностей через діалоги додавання й редагування; рядки замовлення — у вікні замовлення |
| Пошук за кількома полями | Замовлення: держномер, ПІБ клієнта, телефон; клієнти: ПІБ, телефон, email; авто: держномер, VIN, марка |
| Сортування ≥ 2 полів із пріоритетом і напрямком | Панель «Сортування»: поле 1 (↑/↓) і поле 2 (↑/↓) на кожній сторінці з таблицею |
| Фільтрація ≥ 3 умов одночасно | Замовлення: статус, механік, період приймання, «лише прострочені»; склад: категорія, «лише нижче мінімуму», діапазон ціни |
| Скидання пошуку й фільтрів | Кнопка «Скинути» на кожній сторінці |
| Операція предметної області | Оформлення замовлення, додавання запчастин зі списанням зі складу (транзакція), зміна статусу з перевіркою переходів, розрахунок вартості |
| Імпорт / експорт | Експорт поточної (відфільтрованої) таблиці в CSV і JSON; імпорт приходу запчастин із CSV з перевіркою структури, значень і дублікатів |
| Підсумкові показники | Головна: відкриті й прострочені замовлення, виручка за місяць, середній чек, запчастини нижче мінімуму |
| Візуалізація (додатково) | Matplotlib у PyQt5: виручка по місяцях, топ робіт, завантаженість механіків, з вибором періоду |
| Автооновлення пов'язаних подань | Сигнал `data_changed` від сервісів, на який підписані всі сторінки |

Приклади вимог, які можна перевірити:
- «Після повторного запуску програма показує раніше збережені замовлення, а демо-дані не дублюються».
- «Програма не дає зберегти авто з держномером, який уже є в базі, і показує пояснення».
- «Неможливо додати до замовлення більше запчастин, ніж є на складі; залишок не змінюється».
- «Після скасування замовлення залишки запчастин на складі повертаються до попередніх значень».
- «Оплачене замовлення не можна редагувати: кнопки неактивні, підказка пояснює причину».

## 5. Об'єктно-орієнтована модель (попередньо)

> Остаточна модель із діаграмами класів — у `docs/02_design.md`, розділ 2.2. Там вона розширена:
> статуси реалізовано патерном «Стан», транзакції — через Unit of Work, фільтри й поля форм — поліморфними
> класами.

- **Інкапсуляція:** класи моделей (`Client`, `Car`, `Part`, `Order` …) перевіряють значення через `@property`:
  формат телефону й держномера, VIN, рік випуску, невід'ємні ціни й залишки.
- **Композиція:** `Order` містить `Car`, `Employee` і списки рядків (`WorkLine`, `PartLine`) та керує ними
  (додати, прибрати, порахувати суму); `Car` містить власника `Client`; сервіси містять репозиторії;
  `MainWindow` містить сторінки.
- **Успадкування:**
  - `Person` → `Client`, `Employee` (спільні ПІБ, телефон, перевірки);
  - `OrderLine` → `WorkLine`, `PartLine` (спільні кількість, ціна, `total()`);
  - `BaseRepository` → репозиторії сутностей (спільні `get_by_id`, `delete`, безпечний `ORDER BY`);
  - `BaseEntityDialog` → діалоги форм; `BaseTablePage` → сторінки з таблицями.
- **Поліморфізм:**
  - `Order.total()` проходить по всіх рядках через спільний інтерфейс `OrderLine`: `total()`,
    `discounted_total(policy)`, `describe()`. `PartLine` додатково впливає на склад, `WorkLine` — на
    нормо-години механіка;
  - знижки: `NoDiscount`, `ManualDiscount`, `LoyalClientDiscount` з методом `apply(line)`; замовлення не знає,
    яка саме політика застосовується;
  - експортери `CsvExporter` і `JsonExporter` зі спільним методом `export()`.
- **Статуси** — `Enum OrderStatus` із таблицею дозволених переходів, щоб правило було в одному місці.

## 6. Графічний інтерфейс (структура)

Головне вікно з боковою навігацією:

```
┌───────────────┬──────────────────────────────────────────────────────┐
│  Автосервіс   │  Замовлення                     [+ Нове замовлення]  │
│               │  Пошук: [держномер / ПІБ / телефон]  [Скинути]       │
│ ▸ Головна     │  Статус [▾]  Механік [▾]  Період [з..по]  ☐ Простроч. │
│ ▸ Замовлення  │  Сортування: [Дата ▾][↓]  потім [Сума ▾][↑]          │
│ ▸ Клієнти     │ ┌────┬──────────┬──────────┬────────┬────────┬──────┐ │
│ ▸ Автомобілі  │ │ №  │ Авто     │ Клієнт   │ Механік│ Статус │ Сума │ │
│ ▸ Механіки    │ ├────┼──────────┼──────────┼────────┼────────┼──────┤ │
│ ▸ Прайс робіт │ │ 41 │ AT1234BC │ Іваненко │ Петрук │ В роботі│ 3 450│ │
│ ▸ Склад       │ │ …  │          │          │        │        │      │ │
│ ▸ Статистика  │ └────┴──────────┴──────────┴────────┴────────┴──────┘ │
│               │  [Відкрити]  [Змінити статус ▾]  [Видалити]  [Експорт]│
└───────────────┴──────────────────────────────────────────────────────┘
```

Сторінки:
1. **Головна:** картки показників (відкриті, прострочені, виручка за місяць, середній чек), список запчастин
   нижче мінімуму, сьогоднішні замовлення.
2. **Замовлення:** таблиця, пошук, фільтри, сортування, експорт. Вікно замовлення: шапка (клієнт, авто,
   механік, скарга, термін), вкладки «Роботи» і «Запчастини» з кнопками додавання, підсумок зі знижкою,
   кнопки переходу статусу.
3. **Клієнти:** таблиця й деталі вибраного клієнта (його авто та замовлення).
4. **Автомобілі:** таблиця й історія ремонтів вибраного авто.
5. **Механіки:** таблиця, кількість відкритих замовлень, деактивація.
6. **Прайс робіт:** довідник робіт і категорій.
7. **Склад:** запчастини, прихід, імпорт CSV, підсвічування нижче мінімуму.
8. **Статистика:** графіки Matplotlib з вибором періоду.

Пов'язані об'єкти обираються за зрозумілими назвами: «Іваненко Петро, 067…», «AT1234BC — Toyota Corolla».

## 9. Питання до узгодження з керівником

- Чи погоджено SQLite як СКБД (методичка дозволяє й MySQL).
- Склад таблиць (10) і набір операцій предметної області з розділу 3.
- Чи потрібен окремий облік оплат (часткова оплата, передоплата). Зараз його немає.
